## 1. Completed observable behavior

1. **One authority port.** `TeamDomainPort` (`src/domain/team-domain-port.ts`) is the sole abstraction for authoritative roster, task board, mailbox, budget and memory state; `TeamDomain implements TeamDomainPort` and persists through one `TeamAggregateStore`. All 14 `agent_swarm_*` tools and the orchestration runtime consume only this port.
2. **Official Storage Domain Provider.** `StorageDomainTeamStore` (`src/storage/storage-domain-team-store.ts`) opens the official `agent_swarm` domain (`src/storage/team-spec.ts`: `defineDomain`, version 1, zod-validated `teams` + `migration_receipts` tables) and stores one versioned Team aggregate record per Team, partitioned by canonical workspace scope (resolved session cwd). Transactions serialize on per-team and per-scope promise chains; every write reaches backend durability through the official domain write chain before it becomes visible to reads or waiters; `domain/changed` events wake revision waiters.
3. **Fail-closed composition.** `inject = ['tools','subagents','agents','systemPrompt','sessionPersistence','storageDomain']`. A Profile missing persistence or the storage form never activates the plugin (composition-tested three ways: bare, persistence-only, storage-only — `ctx.get('agentSwarm')` stays undefined and no tools register). `apply()` awaits the domain open, so a bad backend route, unit version mismatch or invalid stored record fails plugin activation instead of a later tool call.
4. **Legacy store demoted.** `FileTeamStore` (`src/storage/team-store.ts`) has no write path at all: it is a read-only legacy aggregate reader (`read`/`list`/`pathOf`) plus `resolveStateRoot` for migration discovery. The runtime never constructs it.
5. **Explicit one-way migration.** `migrateLegacyTeamStore` (`src/migration/migrate-legacy-store.ts`) + `scripts/migrate-legacy-team-store.mjs`: per Team — validate the legacy aggregate (`assertTeamState`), require an empty destination (same-id record anywhere in the domain, or an active team of the same captain in the destination scope, abort), durably import through the port, deep-verify the authoritative read-back, then retain a durable receipt (`teamId`, `scope`, `sourcePath`, source SHA-256, verified revision, timestamp). Re-runs are idempotent `already-migrated` skips; a receipt without its record aborts as an inconsistent destination. Legacy source files are never modified. There is no runtime automatic migration, dual-write or fallback of any kind.
6. **Workspace tamper denial.** In the real rc.8 composition the shared workspace contains no Team state files; the aggregate lives in the storage root's `agent_swarm.json` unit; a decoy `.dsh-agent-swarm/<team>/team.json` written by an ordinary workspace writer (claiming captaincy and zeroed budget) cannot alter authoritative state — `agent_swarm_status` returns the true budget after tampering.
7. **Deployment packaging.** `package.json`: runtime dependency `zod ^4.4.3` (record schemas, matching the official storage-domain package), peers `@deepseek-ai/dsh-storage-domain` and `@deepseek-ai/dsh-session-persistence` added; dev dependencies mount the real hub/json backend for tests. `cordis.patch.yml` keeps only the agent-swarm row and documents the required storage-stack composition; README carries the full Profile example with the "storage root outside team workspaces" requirement.

## 5. Official seams, authority and failure model

| Seam | Use |
|---|---|
| `ctx.storageDomain.open(spec)` | runtime + CLI open the `agent_swarm` domain; `Domain.close()` on dispose frees the unit name (tested) |
| `KvTable.put/get/entries` | teams + migration_receipts records; writes durable-first, memory-second, event-third |
| `domain/changed` | store listens and wakes `waitForChange` waiters per team id |
| `sessionPersistence` (service key) | required inject for durable member/crash semantics (F5) |
| `dsh-storage` hub + `dsh-storage-json` backend | deployment/test composition; unit = `<root>/agent_swarm.json` |

Failure model (each tested): missing injected service → plugin pending; unopenable domain (bad route/version/corrupt record) → activation failure (`version-mismatch`, `invalid-record`); backend write failure → transaction rejects, authoritative state untouched, no revision bump; closed store → `TEAM_STORE_CLOSED` for reads/writes and pending waiters; zod-valid but semantically invalid record → `TEAM_STATE_CORRUPT` on read without absolute-path disclosure; store ack is **not** claimed as proof of target-Session receipt (mailbox semantics unchanged, M1B handoff below).

## 6. Migration behavior and rollback evidence

- Success path (tests + real CLI run): legacy fixture → validated → imported → read-back verified → receipt with source SHA-256 → source byte-identical (`Get-FileHash` equal before/after in the CLI run; `toEqual` deep equality after a full storage reopen in tests).
- Idempotent re-run: `already-migrated` skip, exit 0. Named missing team: explicit `TEAM_NOT_FOUND`, exit 1.
- Non-empty destination (same id, or same-captain active team in scope): abort `TEAM_ALREADY_EXISTS` / `TEAM_ALREADY_ACTIVE`, no record, no receipt. Invalid legacy JSON/shape: abort `TEAM_STATE_CORRUPT`, nothing written. Injected backend failure mid-import: abort, no receipt, retry succeeds after recovery. Receipt-without-record: abort `TEAM_MIGRATION_INCONSISTENT`.
- Rollback: sources are never modified, so reinstalling the pre-M1A plugin version reads the untouched workspace state. This is documented in README and §5 of the CLI header.

## 8. Known limitations and M1B handoff

- Process-local store. The per-team/per-scope chains and the official write chain are single-process serialization only; no cross-process CAS/leases/fencing (M7). No cross-process change push.
- Tamper denial covers ordinary workspace writers with the storage root outside the workspace and sandbox roots. It is **not** a defense against a process with unrestricted host access; host sandbox/credential boundaries remain authoritative.
- Whole-aggregate writes remain per transaction (one Team revision = one durable record write); the unbounded attempt/message growth drivers (F6/F7) are M1B and keep the record growing until then.
- `findMembership` still resolves the first active-team match; live-status scheduling, bounded disposal, untrusted-content delimiting and the other accepted findings stay in their milestones (M1B/M1C), per ADR-0007's remediation order.
- **M1B handoff (exact)**: (a) fold target inbox/history by stable Team message id before send/ack to close the F2 crash window; (b) reconcile provisioning from the persisted child descriptor, exact parent and admitted initial inbox/history, then activate or drain (F3); (c) per-target pending mailbox quota with bounded retained receipts, replacing the lifetime `maxMessages` count (F6); (d) bounded/pruned attempt history without re-validating stale attempt ids (F7). The `TeamDomainPort`/`TeamAggregateStore` boundary, the real-stack test harness (`tests/helpers/storage-stack.ts`) and the fault-injection backend are ready seams for that work.
