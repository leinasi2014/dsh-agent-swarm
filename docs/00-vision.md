# 00. 产品愿景与体验边界

## 1. 愿景

用户只需向 Main Brain 描述结果，不必手工管理一组聊天窗口。Main Brain 创建独立 Captain；Captain 根据目标选择成员、模型、Skills 和工具边界，建立依赖任务并对结果负责。用户随时可以在统一 Workbench 中查看多个 Team，或进入某个 Captain Chat 直接干预。

```text
用户目标
  → Main Brain 创建 managed Team，并把完整目标交给独立 Captain
  → Captain 设置公开目标/公告，招募有身份和能力边界的成员
  → Captain 建立任务 DAG，Scheduler 或 Workflow 分派 ready work
  → Member 在当前 attempt 的真实执行根中工作并提交证据
  → Review Gate 接受、拒绝或要求 rework
  → Workbench 从同一 Team authority 展示状态
  → 用户继续由 Main Brain 跨 Team 统筹，或打开 Captain Chat 调整单个 Team
```

需要先审计划时，Main Brain 可先创建没有 Captain 的 staged Team，提交成员和任务计划，经批准后再激活并创建会话；放弃计划只归档草稿。默认 managed create 仍直接启动独立 Captain。

## 2. 三层身份

| 身份 | 职责 | 不能做什么 |
|---|---|---|
| Main Brain | 接收用户目标、创建/列举多个 managed Team、路由用户关注 | 不能冒充 Captain 修改 Team，不能在建队后轮询独立团队 |
| Captain | Team 唯一负责人；招募、建任务、分配、公告、审核和恢复 | 不能把模型声明当作已验收结果，不能批准自己的发布候选 |
| Member | 在一个 fenced attempt 内完成专业任务并提交证据 | 不能调用 Captain-only 管理面，不能写入陈旧 attempt |

名称、职业、性格、简介和安全像素头像是可展示 identity profile；真正权限来自官方 live Agent/Session 绑定和 Host 验证，不来自显示名称。队长分配职责与专业职业，队长和成员分别选择自己的四项文字、保存并读回，再最后设计头像；临时任务与权限约束不代替个人身份。

## 3. 产品界面

- **Main Chat** 保持 Main Brain 会话，不因选中 Team 而改名。
- **Team 卡片列表** 在官方右侧栏内纵向展示并切换多个 Team。
- **Workbench** 参考 `dsh-agent-teams` 的信息层级：公共目标、按真实任务状态汇总的进度、Captain → 成员 → 当前任务执行树，以及可展开的任务依赖。未提交计划、空公告和技术诊断不占据默认概览。
- **Tasks / Announcements / Management** 提供互斥视图；成员详情在本人分支内展开，任务等详情在栏内切换。具体布局、返回与窄屏规则统一见 [UI 布局设计](10-team-ui-layout.md)。
- **Captain Chat** 使用官方 Session navigation 打开所选 Captain；不是 `/swarm` 的隐式写操作。
- **Management** 可向本队 Captain 排队请求调整交流强度，权威读回后才显示已应用；队长也可直接设置本队覆盖。
- **Plugin settings** 配置 Captain/成员模型、Skills、工具 policy、默认交流强度、编排/review 选择和资源上限；保存后由官方 Settings 在重启时应用。未覆盖的模型路由继承用户当前 Session，验收模型不成为产品默认。

UI 必须诚实显示 unavailable、stale、reconnect 和 error。没有权威数据时显示未知或不可用，而不是从 transcript 或本地缓存猜测。

整体架构、会话关系与路由链路见 [Team 总体架构](03-capability-family.md)。会话顶部短名称与团队公共群聊的待讨论方向均在 [UI 布局设计](10-team-ui-layout.md) 中明确范围；公共群聊不属于这里的现有 Captain Chat。

### 3.1 团队公共群聊：功能设计，尚未实现

群聊成为进入单个 Team 的公共协作入口。左侧团队菜单可整体收起，每个团队也可折叠成员；点击团队进入群聊，点击其下成员进入该成员的个人 Chat。右侧以头像网格展示群成员，单击打开资料卡。聊天入口集中在左侧，不再增加“个人执行 Chat”分组标题或资料卡中的重复聊天按钮。界面细节以 [群聊 UI 设计](10-team-ui-layout.md#8-待讨论团队公共群聊) 为准。

| 功能 | 设计行为 | 边界 |
|---|---|---|
| 直接输入与 @ | 输入 `@` 弹出本队成员候选，选择后形成绑定成员身份的提及；无提及时由 Captain 接收。多个明确提及按成员去重后分别投递 | 提及表示处理目标，群内仍公开；第一版不提供 `@全体` 自动唤醒 |
| 图片附件 | 通过图片按钮、粘贴或拖放加入草稿，可预览、移除、重试，也可仅发送图片 | 本轮仅设计图片入口，视频保留为范围外；数量、大小、格式使用目标 Host 的真实限制 |
| 自主视觉协助 | 不支持看图的接收人得到文字请求和可授权转交的图片引用；它根据队员目录，自主请能够看图的队员解释图片，再继续自己的任务 | 群内显示协助关系、相关图片及回答引用；转交识图不自动变更任务负责人、审核人或该成员模型 |
| 队员彼此了解 | 所有队员都能读取同队完整共享资料：名字、职责、职业、性格、简介、Skills、工具可用性、当前模型、图像能力与当前任务 | 资料变更要在后续处理前刷新；技能分配与实际可见性、能力未知与不支持分别表达；私有记忆、凭据和私密执行内容不属于共享资料 |
| 可追溯公开回报 | 群消息可引用原消息、图片、任务和协助结果；任务提交、审核及返修按权威事件展示 | 公开消息、投递排队、模型实际消费分别记录；提交不算完成，不展示推测的全员已读 |
| 连续使用 | 各群聊及个人 Chat 保留独立草稿与附件；关闭页面或重启后可恢复已提交的公开消息和处理进度 | 未提交草稿是否跨浏览器恢复单独说明；重试不产生重复派工或重复公开结果 |

“公开协作”是可见范围，不能兼作调度模式名称。群头预留“发言模式”菜单，基线方案是 **队长协调**；**轮流发言（round-robin）**、**自由发言**仅记录为后续扩展，本次不实现调度或实际模式切换。这里的轮询指轮流安排发言，不指浏览器定时查询；模式也不同于现有交流强度设置。

| 扩展模式 | 产品行为草案 | 实现前需解决 |
|---|---|---|
| 队长协调 | 无 @ 的用户消息默认由队长接收，队长分工，定向交流可唤醒指定成员 | 用户消息、公开回报与任务调度的关联 |
| 轮流发言 | 参与者按轮次依次回应，跳过退出或不可用成员 | 轮次与发言权持久化、超时、跳过、用户插话、轮数/预算上限与重启恢复 |
| 自由发言 | 成员可主动提交公开消息，按权限和运行预算处理请求 | 竞争与公平性、同题合并、回应风暴抑制、结束条件、忙碌成员排队及用户停止 |

模式改变须由有权限的人或 Captain 发起，经 Host 接受后再显示生效；仅打开菜单、查看规划说明不能改变运行策略。后续实现顺序先验证“@ / 图片 → 原接收人 → 同队视觉协助 → 回报与审核 → 重启恢复”，再考虑其他发言模式。

### 3.2 团队目标与任务协作：选定方向，新增机制尚未实现

群聊采用“团队目标 + 现有任务栏”。群头显示可展开的目标摘要，右侧默认任务列表；公告作为有来源和时间的通知，保留在群消息与群信息中。目标说明预期结果，任务说明具体行动；目标不借公告保存第二份，任务也不从聊天文本推算。该方案保留讨论与任务同时可见，避免独立大看板抢占聊天主区。

| 对象 | 产品含义 | 推进与完成条件 |
|---|---|---|
| 团队目标 | 期望结果、完成标准、范围与约束 | Captain 对照标准确认达成，不能由任务完成数量自动判定 |
| 正式任务 | 可执行工作、依赖、优先级、执行者与验收 | 继续使用现有创建、认领、attempt、提交结果与审核流程 |
| 工作请求 | 用户/Main Brain 提出的工作，或成员主动提出待讨论事项 | 实际创建成功后才关联正式任务；提交请求不等于已经派工 |
| 公告/置顶消息 | 有时间和来源的通知或重要讨论 | 不因置顶就获得目标或执行指令的地位 |

用户与 Main Brain 默认“提出任务”，由 Captain 整理、去重、补充依赖并纳入现有任务；明确且已授权的要求可直接处理，不增加逐项用户审批。Main Brain 保持在 Team 外。成员保留当前授权范围内直接创建、认领和提交结果的能力，范围不清或需要讨论时才提出建议；本设计不把所有成员工作强制改为 Captain-only 发布。界面区分原始提出人、实际创建者、执行者与验收者，不能把 Captain 落库等同于 Captain 提出，也不能让浏览器冒充当前查看成员。

任务默认保留现有自动分配，专业工作仍可指定成员。新增“开放认领”作为明确的任务策略：只有已开放且满足依赖的任务显示“待认领”，它不参加自动派工，也不同时指定固定成员。队员按优先级、实际能力和可用性选择，再考虑熟悉程度；不增加虚构熟悉度分数、竞价或逐项审批。重要任务无人领取时，由 Captain 在下一次推进检查中明确指派、拆分或报告能力缺口，不能静默抢领或让队员反复查询。

“完成即结束”与“持续维护”是目标的工作方式；待开始、推进中、暂停、待命、已达成是可见推进状态，不与发言模式混为一谈。持续维护还需要明确触发条件、检查周期及预算；一轮任务完成后等待下一条件，不假装一直忙碌。用户明确要求开始或继续时可据既有授权推进，只有保存草稿才保持待开始，不要求再次机械确认。

目标调整须区分“已保存”与“Captain 已按新目标调整任务”。现有任务由 Captain 明确保留、停止或替换，在途 attempt 不随目标文字被重写。暂停的首版语义是“暂停新增工作”：停止产生新 attempt，已分配、排队或执行中的工作允许收尾；与立即停止执行、归档及发言模式切换分别处理。

当前公共目标和公告有耐久保存入口，成员可创建/自领任务，未指定成员的 ready 任务会自动分配；这些现有能力不等于开放认领通知、目标持续规划或暂停控制已经实现。实现顺序先完成“人类提出 → Captain 整理 → 现有任务 → 审核与群内回报”，再分别实现开放认领和持续目标机制。架构边界见 [6.5 节](03-capability-family.md#65-目标推进与任务认领的候选扩展)，界面见 [8.6 节](10-team-ui-layout.md#86-团队目标与任务面板的选定方案)。

## 4. 技术位置

DSH 的 Session、Agent、Subagent、Tools、Workflow、Storage、Settings 和 Client slots 都是官方能力。本插件只在这些 seam 上组合：

```text
Service Definition → Provider → Consumer → Bundle/Profile composition
TeamDomainPort      → StorageDomainTeamStore → tools / Host / RPC / UI
```

项目不会注册第二个 `ctx.agentTeams`。官方 experimental Agent Team 已在固定版本发布，但尚未被本插件采用；当前 `TeamDomainPort` 隔离 project-owned provider。未来采用官方实现须核验身份、持久化与迁移合同，并保持单一权威。

## 5. 支持范围

当前产品方向包括 durable Team、任务/attempt、邮箱、budget、review、memory、Skills/tools policy、Workflow/Jobs bridge、execution roots、Host/RPC、DSH Workbench、设置、迁移和受控发布。

以下是后续能力而非现有承诺：远程成员、跨进程 distributed Team store、通用 browser direct writes、Canvas-native Consumer、自动 Skill Evolution 和公共市场发布。

## 6. 成功体验

面向用户的完整代表场景是：

1. 在 fresh isolated official DSH Profile 安装不可变插件包并启动。
2. Main Brain 创建至少两个独立 Captain Team。
3. Captain 设置目标/公告，招募带不同 Skills、模型和工具 policy 的成员；各人完成自己的身份文字、读回和头像。
4. 一个含依赖的任务 DAG 经分配、执行、提交、验证、接受和失败恢复完成。
5. Workbench 原位切换 Team，所有身份、任务和活动与权威读回一致；Captain/Member Chat 导航到正确 Session，面板交流强度请求经队长保存并读回。
6. 重启后状态恢复；禁用、卸载、升级和回滚不泄漏 listener、route、timer、Session 或 storage authority。

这个场景通过真实 Profile/browser 和持久化重启证据后，才支撑对应产品 claim。目标设计、单元测试或截图不能单独替代它。
