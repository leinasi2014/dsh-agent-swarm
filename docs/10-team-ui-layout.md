# 10. Team UI 布局与交互设计

本文件定义 Team 界面的信息层级、布局和交互。总体架构见 [03-capability-family.md](03-capability-family.md)，身份、读权限、导航与状态合同见 [04-core-protocol.md](04-core-protocol.md)。除第 8 节明确标出的群聊讨论稿外，其余内容是当前改版的设计与验收要求；是否已在目标环境交付，须看对应候选的真实浏览器证据，不能由本文或示意图判定。

## 1. 用户要看清什么

进入页面后，用户应能直接识别当前在和谁对话、这个人属于哪个 Team、谁是队长、任务正在推进还是等待处理，以及在哪里打开个人对话。多 Team 共用一个工作界面；Main Brain 主会话保持自己的身份。

| 区域 | 主要问题 | 主要信息 |
|---|---|---|
| 官方会话栏 | 我打开的是哪个会话？ | 官方 Session 名称与列表 |
| 中央会话顶部 | 当前是谁、属于哪个团队？ | 主会话 → 短 Team 名与队长名 → 成员名、官方子会话计数 |
| 中央对话 | 当前这个 Agent 在做什么？ | 该 Session 的消息、工具结果和官方输入栏 |
| 右侧 Team 页签 | 全队进展如何？ | 多团队卡、进度、待办、Captain → Member → 当前任务 |
| 成员详情 | 这个人具备什么、正在做什么？ | 个人资料、当前任务、运行、Skills 与工具、成果与成长 |
| 官方插件设置 | 新建团队使用哪些默认配置？ | provider/model、Skills、工具策略、交流与资源配置的已支持项；推理等级由工具调用参数指定 |

│ 其他会话     │                                   │ 归属：主会话 › 星河 › 衡准 │

Team 页面复用官方 SidebarRight 的独立页签。关闭后，从官方新页签引导页重新打开；不在中央会话顶部另加 Team 按钮。自动显示须等待完整、属于当前 Session 的 Host 投影；用户关闭、切换页签或收起侧栏之后，正常刷新不抢回焦点。具体首次挂载与 Session 寻址合同由核心协议定义。

## 3. 团队卡与执行树

同一主会话的关联 Team 纵向排列，每个团队一张卡。默认展开一个团队，其余保持摘要；进入队长或成员 Chat 时优先定位其真实所属 Team，用户显式选择的其他 Team 按当前 Session 保留。

```text
▼ 星河                 活跃             [打开队长对话]
  队长 北辰 · 成员 2 · 已完成 3 / 5
  进度：完成 3 · 执行 1 · 待审核 1
  待处理：1 项审核
  [公开目标 ▸] [最新公告 ▸]
  [概览] [任务] [公告] [管理]

  北辰  队长
  ├─ 衡准  质量验证     验证中      [打开对话]
  │  ├─ 当前任务：检查交付结果
  │  └─ 成员详情（点击本人后原位展开）
  └─ 砺行  功能实现     执行中      [打开对话]
     └─ 当前任务：完成实现
```

卡片摘要来自同一个 Team projection。已完成数只统计 canonical completed；submitted 显示待审核。未知依赖显示“依赖状态待确认”；截断读取应提示已显示范围，不生成虚假的总体百分比。没有计划、空公告和技术诊断不占据默认概览；折叠目标和公告不折叠进度与待处理事项。

成员行按 Captain → Member 缩进，当前任务位于该成员下方。只关联当前 attempt；旧任务、旧身份、移除成员不能继续显示为当前工作。当前会话标记与正在查看的 Team 卡是两个信息：查看另一个 Team 不等于跳转到它的 Captain。

| 卡内视图 | 默认内容 | 操作结果 |
|---|---|---|
| 概览 | 真实进度、执行树、当前任务与待处理事项 | 展开成员、打开个人对话或任务详情 |
| 任务 | 任务清单、真实状态、已有依赖图 | 进入栏内任务详情，返回恢复原入口焦点 |
| 公告 | 队长发布的公开公告 | 展示有来源的内容与时间 |
| 管理 | 已支持的团队管理请求与诊断入口 | 交流强度请求排入队长会话；权威读回后才标记已应用 |

## 4. 成员详情与任务详情

成员详情在本人分支内展开，不覆盖中央会话，也不创建第二个成员导航栏。成员身份与当前任务始终位于其三个详情页签之外。

```text
└─ 衡准  质量验证                             [打开对话]
   头像  姓名 / 职责 / 职业
   性格、简介、已知模型信息
   当前任务：检查交付结果 · 执行中 · 开始时间
   ┌─────────┬──────────────┬────────────┐
   │ 运行    │ Skills 与工具│ 成果与成长 │
   └─────────┴──────────────┴────────────┘
   所选页签的资料
```

运行页展示官方组合可读的 provider、model、preset 与状态；资料中保存的模型不能冒充最新请求已使用的模型。Skills 展示 Team allowed、成员 assigned、Session-visible 等各自已支持的投影；工具按实际可见/限制信息呈现。成果只显示有来源的输出与记录，不能从职业、头像或记忆推断成长。成员私有记忆保持私有。

任务、预算和诊断详情沿用栏内切换与明确返回入口；不使用 modal、absolute 详情遮罩或插件自有全屏回退。长资料单行省略并提供完整文字访问，普通正文在栏内换行，局部横向内容按需滚动。键盘用户可到达操作与返回入口，焦点不能掉回页面起点。

## 5. 会话顶部短名称

此项是当前改版需要接入的显示规则，依赖 Core 的通用 lineage display seam；正式安装与浏览器未验证前，不能把源码或测试截图作为已上线证明。

| 对象 | 可见文字规则 | 完整信息与回退 |
|---|---|---|
| Main Brain | 保持官方主会话名称 | 选中 Team 不改名 |
| Captain | `短 Team 名 · 队长自定名` | Team 名最多取 6 个 Unicode 码点，再加省略号；完整 Team/队长名保留在悬停文字 |
| Member | 成员自定显示名 | 无自定名时用真实 roster 名；悬停显示 Team、Captain → Member |
| 后代数量 | `xN` | N 取官方控件提供的后代计数，不用 Team roster 数替换；完整含义沿用官方可访问标签 |
| 关系不明或数据不可用 | Core 原始文字 | 非 active、错误父级、成员已移除、非 continuable、stale 或不完整读回不得显示猜测名称 |

同一规则应用于官方顶部 lineage 行和官方切换列表的对应文字槽。插件只提供文字，导航、选中、展开、计数来源与可访问性由官方控件拥有。身份随权威读回更新，不复制一份姓名缓存或启动第二个轮询器。

## 6. 窄屏、状态与输入区

窄屏由官方宿主决定右栏分栏或浮动；Team 内容始终适应实际容器宽度，不能依赖浏览器外窗宽度假定存在三列。卡片、树和详情在栏内纵向流动，长名称不会撑宽页面。

```text
官方宿主打开 Team 时：
┌────────────────────────────┐
│ 官方返回 / 关闭    Team     │
├────────────────────────────┤
│ 主会话 › 星河 › 衡准       │
│ ▼ 星河 · 北辰              │
│   进度与待处理事项         │
│   概览 / 任务 / 公告 / 管理 │
│   北辰                    │
│   └─ 衡准                 │
│      当前任务与成员详情   │
│ ▶ 远山 · 司南              │
└────────────────────────────┘
```

| 状态 | 页面表现 | 操作边界 |
|---|---|---|
| 首次读取 | 明确加载提示；没有完整 Team 关系时不显示伪空卡 | 不把上个 Session 正文挂到新目标下 |
| 无团队 | 保持官方会话体验 | 不强行打开空 Team |
| 断线 / 陈旧 | 概览与详情同时提示，已有内容有明确陈旧标记 | 未重新验证的地址与绑定不能当作当前事实 |
| 重连 | 读取当前目标并恢复可验证内容 | 不抢回用户关闭的侧栏或页签 |
| 导航失败 / 成员不可用 | 显示失败或不可用原因 | 不猜 URL，不向另一会话发送操作 |
| staged Team | 明示尚未创建 Captain | Captain Chat 入口不可用 |
| 已归档 | 明确历史阶段 | 不伪造 active 成员或当前工作 |

中央输入区复用官方 Composer。当前会话可停止时保留 Stop；发送能力不可用时不应并列显示一个会误导用户的 Send。该行为归 Core 会话 UI，须按实际在线、离线和运行状态独立验证；Team 管理消息的队列状态不能代替官方输入状态。

## 7. 验收场景与实现入口

验收用例见 [08-testing-verification.md](08-testing-verification.md)。下列结果必须在实际官方布局中观察，不能只靠组件 fixture：

1. 主会话下至少两个 Team：卡片纵向排列，切换只读目标时没有旧正文串入。
2. 进入成员 Chat：官方顶部显示正确队长/成员短名，侧栏标记其所属 Team；点击返回主会话，落到精确 root Session。
3. 第一遍打开、快速来回切换、侧栏关闭和其他页签选择：无错误 Session 页签、焦点抢占或重复监听。
4. 成员身份更新、移除与父级不匹配：正确更新或回退，官方数量不被 roster 数覆盖。
5. 成员详情、任务详情、长文本、窄栏、官方浮动布局、键盘操作与读屏名称：信息可读、操作可达。
6. 加载、断线、重连、归档及 staged Team：状态诚实，权限仍由 Host 验证。
7. Captain 显式路由和自身换模型：用真实请求与冷恢复证明路由，不能只验设置页文字。

## 8. 待讨论：团队公共群聊

本节定义“Team 主入口为公共群聊，每人保留独立执行 Chat”的设计提案。此轮交付是设计文档和交互原型，尚未实现群聊 runtime。功能范围见 [产品设计](00-vision.md#31-团队公共群聊功能设计尚未实现)，消息权威、共享目录和自主视觉协助见 [候选架构](03-capability-family.md#61-公共群聊的候选架构)。第 1–7 节仍描述现有个人会话工作台，不能把其中行内成员详情的规则套用于此群聊资料卡。

### 8.1 候选布局

```text
┌──────────────┬─────────────────────────────┬──────────────────────┐
│ [团队栏收起] │ 星河 · 群聊   [队长协调⌄] │ 任务 / 成员 / 群信息│
│ ▼ 星河 群聊  │ 群成员数 / 置顶公告        │ 头像 头像 头像 头像 │
│   北辰 队长  ├─────────────────────────────┤ 姓名 姓名 姓名 姓名 │
│   砺行       │ 用户：@砺行 请检查这张图   │ 单击打开成员资料卡  │
│   衡准       │ [图片缩略图]                │                      │
│ ▶ 远山 群聊  │ 砺行 → 衡准：请协助看图    │                      │
│              │ 衡准：引用图片的检查结论    │                      │
│              ├─────────────────────────────┤                      │
│              │ 输入消息，@ 选择成员        │                      │
│              │ [图片缩略图 ×]              │                      │
│              │ [添加图片]          [发送]  │                      │
└──────────────┴─────────────────────────────┴──────────────────────┘
```

左侧呈现位置和 Host 扩展点仍需实际组合验证。团队箭头只折叠该团队下的成员；群名仍可进入群聊。顶部团队栏按钮收起整个导航，群头保留当前 Team 身份。点击左侧成员进入其个人 Chat，不显示“个人执行 Chat”分组标题；右侧资料卡和群消息中不重复增加“打开个人 Chat”按钮。

右侧“成员”采用头像与名字网格：姓名截断时提供完整可访问名称；单击头像打开有明确关闭入口的资料卡，显示身份、职责、职业、性格、简介、当前任务以及“能力 / Skills 与工具 / 成果”页签。职业与本队职责分别展示，不用“负责实现”代替职业。可查看当前模型、支持图片/不支持/未知、资料来源更新时间；分配与实际可用的能力有明确区别。卡片不跳转聊天；Esc 或关闭按钮恢复焦点到原头像，点击其他可操作控件时关闭资料并保留该控件的正常焦点。桌面卡片靠近触发头像，窄屏采用栏内详情或底部资料层，不能挤出可见范围、遮住关闭入口或形成横向溢出。

### 8.2 输入、提及与消息草稿

输入栏不设“交给”下拉框。默认空草稿只提示“输入消息，@ 选择成员”；在没有有效提及时以低强调文字说明“默认由队长处理”。`@` 表示公开消息的处理对象，不是私聊。

| 操作 | 交互规则 |
|---|---|
| 键入 `@` | 在输入区附近打开本队成员候选，按输入检索；中文或标点后直接输入也触发，如 `请@衡准`，不要求前置空格。每项显示头像、名字、职责及图像能力，同名成员要能区分 |
| 选择成员 | 插入绑定稳定成员 ID 的 mention token；消息显示姓名，改名不改变接收身份。已移除/不可用成员不能悄悄替换成别人 |
| 键盘与输入法 | 上下键选择候选，Enter 确认，Esc 关闭；中文输入法组合期间不触发发送。普通 Enter 换行，Ctrl/Cmd+Enter 发送 |
| 多个提及 | 允许多个已确认 token，按稳定 ID 去重后分别定向投递；不提供隐含全员广播。普通文字中仅出现名字不算提及 |
| 手输或粘贴 `@名字` | 尚未确认的提及须提示选择成员，不能猜测同名身份后发送，也不能静默改成默认队长；候选检测与未确认提及检查使用相同起点规则 |
| 编辑 token | 整体删除或重新选择；普通复制来的文本不继承接收权限 |
| 切群或个人 Chat | 按真实群/会话身份保留各自草稿、提及与附件，返回恢复；切换不能把上一群内容发给新目标 |
| 发送过程 | 提交期间防止重复点击；失败保留草稿并可重试。成功清空当前草稿，公共消息显示真实投递状态 |

`@` 候选不覆盖发送按钮或裁出视窗，候选很多时使用有限高度列表；键盘焦点与读屏活动项对应同一个候选。点击成员资料、切发言模式说明或查看任务不应清空输入草稿。

### 8.3 图片附件与自主视觉协助

图片按钮与发送按钮放在输入框底部两侧；支持本地选择、粘贴和拖放。附件缩略图位于编辑区内，可查看文件名和移除。首期只显示图片入口，不把视频列为可用操作。原型的本地图片预览必须标明本地状态，不能声称已上传到 Host。

| 状态 | 用户可见行为 |
|---|---|
| 草稿图片就绪 | 显示缩略图，可移除；允许只发送图片 |
| 读取/上传中 | 显示进行状态，整条消息暂不可提交 |
| 格式/大小/像素不符或上传失败 | 保留草稿，说明原因，可移除或重试；实际限制取自 Host，不在设计中猜固定值 |
| 接收人不支持看图 | 保留用户选择；提示其可请视觉队员协助，不强制用户改接收人，也不自动替换模型 |
| 群内发起协助 | 显示“砺行请衡准看图”，关联原消息和图片；协助摘要回报有来源，原负责人保持不变 |
| 无可用视觉成员 / 能力未知 | 显示“等待视觉协助”或明确能力待确认，原接收人或 Captain 处理；不伪造识图结果 |

群中能查看原图片和相关回答，详尽工具轨迹保留在个人 Chat。图片公开范围与原消息一致；“已上传”“已排队”“视觉成员已处理”不得混成一个成功标记。共享目录由模型可读来源更新，资料卡显示并不证明成员已读取最新信息。

### 8.4 发言模式：扩展记录，不实现运行

将群头原“公开协作”标记改为“队长协调⌄”等发言模式入口。菜单保留简短解释：“队长协调：队长统筹、定向协作”“轮流发言：按轮次依次回应”“自由发言：成员按规则主动参与”。后两项显示“扩展预留”，本轮不执行调度或保存生效；原型可查看规划说明，不演示虚假的轮次与全员自动回复。

公开可见范围由群聊本身表达，不随发言模式改变；现有交流强度也不自动映射到这些模式。以后切换时应显示当前模式、待应用状态及失败原因，并允许用户明确停止/暂停发言调度。轮流与自由模式的权限、并发、预算、终止及冷恢复设计由架构和产品文档记录。

### 8.5 窄屏、异常与验收

窄屏把成员、任务、群信息入口保留在群头附近，通过同一侧栏/抽屉或栏内面板展示，不要求用户滚到整段群聊底部才能查看资料。资料、模式和 `@` 候选互相避让；关闭或返回恢复原入口焦点与未发送内容。至少检查 390px、768px 与桌面宽度。

| 情境 | 验收要求 |
|---|---|
| 草稿与提及 | 无 @、多 @、同名、改名、退出、中文输入法、Enter/Ctrl+Enter、切 Team 后草稿不串入 |
| 附件 | 仅图片、文本加图、多图、格式错误、失败重试、移除和发送中切换；没有视频发送入口 |
| 人员导航 | 左侧成员打开个人 Chat，右侧头像只展示完整资料；折叠不丢当前会话；无重复 Chat 操作 |
| 视觉协助 | 原接收人自主选择视觉队员，引用原图回报、无递归转交或责任暗改；能力未知和无视觉成员有明确结果 |
| 共享目录 | 名字、性格、简介、Skills 和真实能力改变后，UI 与队员读取一致；资料未完整时明示 |
| 模式扩展 | 能查看规划内容，但不误标轮流/自由模式已经生效 |
| 可达性与恢复 | `@` 列表、资料卡、图片操作不裁切，键盘与触摸可达；重连与重启后不重复消息或派工 |

未来实现的最小链路为：用户 `@` 非视觉成员并附图 → 该成员读取同队共享目录 → 自主请求视觉成员协助 → 群内可追溯回报 → 原成员提交 → Captain 审核 → 打开个人 Chat 核对执行 → 重启后继续读回。当前仅交付设计与原型，不把示例内容作为这条链路的实际验收。
