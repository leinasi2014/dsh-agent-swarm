## 1. 部门组织边界

**DEPT-01〔需求 + 定稿设计〕：先部门，再管理员，再招募。** 部门围绕长期职责成立，具有稳定身份。管理员是承担管理岗位的员工；员工与一次任职、一个 Session 不是同一对象。员工只有一个当前直接汇报对象，汇报关系不自动禁止获准的同伴沟通。管理员替换保留部门和员工身份，具体执行接管必须通过合法会话机制验证；不能只改队长名字或历史 Session parent。

**DEPT-02〔定稿设计〕：部门定义包含下列业务信息。** 它们是逻辑要求，不强制每项对应一个手填表单字段。系统能可靠推导的内容自动填充；来源不明不得猜测。

| 信息 | 必须表达的含义 |
|---|---|
| 身份和状态 | 部门 ID、名称、设立主体、当前管理员任职引用，设立/运行/暂停/撤销的处置边界 |
| 使命与产出 | 服务对象、职责、预期成果和质量要求；不能用消息量或 token 消耗代替绩效 |
| 职责边界 | 负责与不负责的事项、依赖和跨部门移交条件 |
| 岗位和能力 | 岗位职责、职业能力、工具条件和最低入职要求；模型品牌不能替代验证 |
| 行为政策 | 表达、探索、流程灵活性、通信范围、实际操作权限五轴分别描述 |
| 管理和沟通 | 派工、人事、验收等动作的授权来源，允许交换的信息范围；不复制权限权威 |
| 知识和资源 | 个人、岗位、项目与部门资料归属，工具和预算引用 |
| 评价和纠错 | 验收依据、允许试错的边界、调查与异议入口 |

**DEPT-03〔需求 + 定稿设计〕：部门允许不同工作风格。** 创作、研究和质量审查可以有不同的表达与探索默认值；不固定部门类型枚举。系统硬约束不能被人格、部门或任务指令放宽。下层只能在上层明确允许的范围内覆盖默认值，保留来源和版本。性格如何生成、谁能改变员工人格、员工如何提出异议，属于 EMP 讨论的待决范围。风格不同不等于记忆污染。

**DEPT-04〔定稿设计〕：组织、项目、协作和执行分开。** 一个部门可以关联多个 Team；一个项目可由多个 Team 协作。项目工作区是长期工作资料的组织范围；attempt 执行根是一次尝试的临时工作副本，二者不要求物理嵌套。不得把跨 Team 项目或长期部门资料的唯一保存位置寄托在任意一个临时 Team 的清理周期上。

部门暂停时阻止受影响的新增工作；已有工作须明确停止或获准移交。撤销前必须有人员去向和资料承接安排，不自动等于解雇全部员工或删除资料。首次任命、代理权限及具体撤销批准者沿用尚待确认的人事权限议题，不允许候选管理员自批。

## 2. 资料室职责与事实归属

**LIB-01〔定稿设计〕：资料室承担保存、登记、定位、版本引用与获准访问。** 它替代零散共享目录的产品入口，底层仍可采用文件和 Git。已有代码、文档不要求搬出仓库；新产生且没有既有保管位置的部门资料，由独立于 Team 生命周期的资料存储保存。

| 对象 | 事实来源 | 资料室的职责 |
|---|---|---|
| 部门、员工、任职 | 合法组织事实来源；实际持久化接入待验证 | 引用身份、当前授权和保管责任 |
| 任务、attempt、验收 | 既有 Team/审核合同 | 引用具体任务、尝试和被审版本，不再建验收队列 |
| 执行过程 | Session 日志 | 提供必要定位，不复制完整聊天权威 |
| Git 管理的代码和文档 | 仓库及明确 commit | 固定版本引用；保存副本不改变仓库归属 |
| 资料室托管文件 | 资料版本登记与受管存储 | 保存内容、位置、版本、完整性和恢复记录 |
| 外部链接 | 外部来源；内容可能变化 | 标为可变引用，或另存获准快照并记录抓取版本/时间 |
| 私人记忆、人格和操作档案 | 员工个人分区 | 不自动扫描、导入或公布 |
| 私人及通用 Skills | 既有 Skills 管理合同 | 只呈现获准引用；纳管不等于发布，发布不等于加载 |

**LIB-02〔定稿设计〕：资料身份、版本和存储位置分开。** 最小逻辑对象是资料条目及其版本。条目有稳定 ID、标题、业务归属和当前版本引用；版本记录来源、创建者/任职引用、内容位置、不可变版本标识，托管内容另有摘要及保存确认。引用至少包含资料 ID 和版本 ID；路径是可变的解析结果。具体 URI 语法、序号或内容摘要选型由技术负责人决定，不为此引入通用引用图服务。

业务归属、创建者、保管者和访问者分别表达。创建者调岗不自动带走部门成果，任职期间创建也不自动把私人资料变成部门资产。历史作者信息的保留范围受已确认删除规则约束，不能用来源追溯为由备份全部个人档案。

**LIB-03〔定稿设计〕：分别展示事实，不合成一个可随意填写的 status。**

| 维度 | 表达和更新规则 |
|---|---|
| 验收 | 引用针对准确内容版本的审核结果；无记录显示未审核。历史通过不自动适用于修订版 |
| 保存 | 区分仅引用、托管保存已确认、登记/保存未完成；归档是保管政策动作，不是验收通过 |
| 可访问性 | 可读、源缺失、内容变化、无权访问等按实际结果区分；未授权者不能借状态提示获得受限元数据 |
| 当前使用建议 | 当前推荐、已替代、已撤回/争议等来自有权主体的决定；替代不等于字节缺失，也不抹掉历史批准 |

资料室保存自己的登记和版本事实，验收和权限结论依赖各自权威。文件正文的 `approved` 等文字不能生成批准。未保存到长期载体的引用不得显示“已归档”。

## 3. 保存、审查与使用流程

**LIB-04〔定稿设计〕：先保全需提交的内容，再提交引用。** 员工明确提交的报告在会回收的执行根中时，Host 先创建可恢复的保存操作标识，将指定内容写入受管暂存位置，核对内容并发布不可变版本，持久登记成功后返回版本引用；之后才向既有任务系统提交该引用。这里的保存动作不依赖审查是否通过。

不声称文件、登记和任务系统有共同原子事务。内容保存成功而登记失败时保留可恢复内容；登记成功而任务提交失败时保留尚未关联/未提交的版本，使用同一操作标识恢复，不能重试一次生成一份新版本。登记不得先宣布正文可读，再尝试保存正文。只有已确认版本可返回成功；恢复记录是存储操作的一部分，不新建业务任务队列。

**LIB-05〔定稿设计〕：审查绑定版本，读取核对当前资格。** 既有审核者审查固定内容版本，资料室引用审核结果。其他 Team 读取该版本时校验当前访问资格，再解析位置与必要完整性；固定版本引用不悄悄跟随新版本。展示“推荐版本”可以解析当前指针，但任务证据必须记录实际使用的版本。无任务的获准导入也可登记，初始未审核，不能伪造任务验收。

**LIB-06〔定稿设计〕：修订新增版本，发布指针检查并发。** 两人基于同一版本修订时都可保存独立候选；更新当前推荐版本须检查预期旧版本/修订号，不允许后写者静默覆盖。冲突保留双方内容并交既有负责者处理，不自动合并。撤回或争议改变当前资格与提示，历史读取是否允许依现行授权；不把历史验收改写为从未发生。

**LIB-07〔定稿设计〕：快照不自动转移正本或授权删除。** 内容摘要只能用于完整性核对。移交保管/正本职责需要明确授权、来源与目标版本、引用更新及结果读回；否则只是副本。多个不可变历史版本不构成多份相互竞争的事实来源。v1 不做自动源文件删除或通用正本迁移。

## 4. 权限、导入和资源回收

**LIB-08〔定稿设计〕：查询、直接读取、导出和写入都检查当前授权。** 部门/项目 ID 和模型提示不是凭证，授权从真实执行身份及合法关系取得。跨部门默认不自动共享；已有明确授权的共享按其范围执行。列不出不等于读不到，已知版本 ID 也不能绕过检查。

v1 可以首先服务同一信任和文件访问范围内的协作。若部署要求受限部门或私人资料隔离，必须先验证文件工具、Shell、其他可达工具及宿主存储的实际边界；否则不纳入该受限使用范围，不报告“已隔离”。资料室不负责自建操作系统沙箱，但不能借此免除自身接口授权或掩盖宿主旁路。正常误操作与持有任意宿主写权限的攻击能力应分开陈述。

**LIB-09〔定稿设计〕：导入内容是资料，不是授权指令。** 允许获准用户/智能体导入文件、外部资料和补录，保留来源与导入身份。导入不自动验收或转成 Skill；正文内命令不改变权限、系统指令或调用工具。读取提供来源和信任边界，实际工具动作仍经过 Host 授权。单个恶意文本测试通过不证明能防御全部提示注入。HTML 等主动内容的预览沿用受限预览能力，相关富媒体 UI 另属其功能范围。

**LIB-10〔定稿设计〕：取消执行与删除工作文件分开。** 取消应及时终止/撤销旧执行，不等待归档完成；尚在执行的写入是否停止须实际确认。提交、失败、重派及回收共用“哪些内容要求保留”的规则，只处理明确提交、登记或按既有策略需要恢复的成果，不复制整个工作区。需要保留而保存失败时阻止相关文件清理，保留有 owner 和恢复原因的残留；其余临时文件继续遵循受管生命周期。Team 解散只能做最终核对，不能作为第一次抢救字节的时点。源已消失只能如实报告缺失并使用已有恢复来源，不能声称事件能重建原文。

重试必须有界，不自动循环调用模型；暂存容量不足明确失败。清理残留的条件由既有回收流程核对，不能以目录年龄或模型自报完成作为唯一删除依据。员工解雇及部门撤销的资料处置按已确认边界办理，混合私人内容先隔离待处理，不静默保留或公开。

**LIB-11〔定稿设计〕：列表不反复扫描正文。** 使用必要的登记元数据、按需分页、定向刷新和延迟读取。可重建索引只是投影，权限在实际操作处重核。缓存、物理文件布局和失效策略由实现负责人根据数据量选择；不强制新增数据库，也不把 Team selector 的规则扩大成全资料室每次实时枚举。首次 v1 不做全文/向量检索、通用依赖图和自动语义分类。

## 5. 第一版切片和验收出口

以下是功能顺序及验收合同，不是滚动任务状态；具体任务和发布记录留在既有动态系统。

| 切片 | 完整可用结果 | 暂不包括 |
|---|---|---|
| A：组织与保管边界 | 稳定部门/项目引用、合法当前管理员引用和独立长期保管位置可重启读回；不伪造尚未支持的接管 | 完整员工成长系统、未定的人事授权 |
| B：登记与引用 | 获准导入或提交资料，得到稳定版本引用，列表浏览、直接读取与失效提示可用 | 全文搜索、向量库、通用图服务 |
| C：提交和恢复 | 临时产物先保全再提交，重试不重复，取消与清理分离，重启可恢复 | 所有临时文件自动归档、自动删除 |
| D：审核与修订 | 复用准确版本的审核，其他 Team 获准读取，并发修订不覆盖 | 第二套审批队列、自动正本迁移 |

A–D 构成本文基础版本的完整出口，可以逐片交付试用；仅完成 B 不得宣称临时执行成果的可靠保存已经完成。实际官方持久化/API 接入、组织关系恢复仍需按项目兼容门验证。受限部门资料的隔离验收是其上线条件，不以同信任范围试用替代。

| 场景 | 必须观察到的结果 |
|---|---|
| LIB-A01：生成报告→提交→审核→另一 Team 获准引用→原 Team 结束→重启 | 同一准确版本仍可定位读取，审核来源可核对，长期保存不依附原 Team |
| LIB-A02：在内容保存、登记、任务提交之间分别注入失败，再重试 | 不出现虚假成功、重复版本或已保存成果被误清理；可恢复缺失步骤 |
| LIB-A03：取消/失败/重派时保存失败或仍有写入 | 旧执行停止状态可核实；需保留内容不被回收，不出现双重执行，恢复不依赖新任务自领 |
| LIB-A04：两名成员基于同一版本并发修订 | 两份内容保留，推荐指针有冲突检查；旧引用和审核不自动指向新版本 |
| LIB-A05：外部链接内容变化、托管文件缺失、版本撤回 | 内容变化、缺失和当前禁用分别显示；不伪造恢复，也不抹去历史验收 |
| LIB-A06：无权列出、持有版本 ID、调岗后重读及文件工具/Shell 旁路 | 资料室接口不泄露受限内容；部署实际边界与声明一致，不能仅用查询过滤证明隔离 |
| LIB-A07：导入含指令的文本/主动内容，再调用工具 | 导入未自动批准，内容未自授权限；具体攻击样例与验证边界可复核 |
| LIB-A08：部门撤销/员工解雇涉及部门成果、私人档案和混合内容 | 按既定分类与授权处置，未决内容不擅自转资产或销毁；必要人事记录不夹带私人正文 |

所有场景目前是待执行合同，不是已通过记录。外部模型共识不代替产品验收。
