# dsh-agent-swarm 产品章程

本文件只定义稳定的产品目标、范围和验收原则，不登记当前任务、负责人、分支、候选、审查结论或里程碑进度。实时工作状态由项目绑定选定的外部 provider 或非提交式动态台账承担；版本化实现与审查结果保存在 Git、阶段报告和 ADR 中。

## 产品目标

以 official-first 的纯插件方式，为 DeepSeek Harness 提供持久、可审查、可恢复的多 Agent 团队协作层。插件应把团队任务、成员、邮箱、预算、审核和调度组合到官方服务 seam 上，并保持一个可恢复的权威 Team 状态。

## 稳定范围

产品能力族包括：

1. 崩溃安全的 Team 聚合、任务 DAG、revision/attempt 围栏和持久邮箱；
2. 可替换的调度、审核、预算、验证、记忆与远程成员 Provider；
3. 官方 Workflow、Jobs、Token Meter、Storage Domain、Workspace 与 Subagent 能力的兼容消费；
4. 稳定控制面、冻结候选、独立验收、外部晋升和可验证回滚；
5. Host/RPC 与 UI Consumer，使用户能观察并指挥团队而不复制权威状态；
6. 插件化发布、迁移、兼容退役和故障恢复。

UI 是末端投影型 Consumer；插件内核保持独立、可替换且不依赖某个 UI 宿主。

## 产品红线

- 不修改 Agent Loop 来实现 Team 专属行为。
- 不影子注册官方服务，不维护两个可写的 canonical 状态机。
- 权威 Team 状态经 TeamDomainPort 落在官方 Storage Domain；模型可见状态可由 Session 记录重建。
- 每个注册、后台活动和外部资源都有生命周期 owner、disposer 和失败可见性。
- Worker、Reviewer、Acceptor、Promoter 的权限按风险分离；候选不能批准或部署自身。
- 参考仓库只提供行为、故障和交互证据，不成为第二运行时。
- 版本、已发布 API 和实际装配事实由清单、锁文件、官方基线、目标安装包和真实 Profile 共同证明。

## 能力演进顺序

路线图按依赖关系组织，不表示实时完成状态：

1. M1：崩溃安全协议、持久化权威和基础独立验收；
2. M2：官方 Workflow/Jobs 桥与多编排 owner 围栏；
3. M3：冻结候选、可执行审查、隔离验收、晋升和回滚；
4. M4：计量、预算与验证能力族；
5. M5：Workspace 与权限能力族；
6. M6：记忆与经验演进；
7. M7：远程成员与分布式协调；
8. M8：生产加固、兼容与运维；
9. M9：客户端/UI 与正式发布。

阶段定义、依赖和出口标准见 docs/07-implementation-roadmap.md。阶段报告和 Git tag 是历史证据，不由本章程汇总成实时状态。

## 产品级完成原则

一个能力只有在以下事实同时成立时才可声明交付：

- 行为落在明确的官方或项目自有 seam，且没有第二权威；
- 持久状态、并发围栏、生命周期和恢复窗口有可执行证据；
- 模型可见工具、提示或投影有结构与语义验证；
- 风险对应的非作者审查绑定到精确候选；
- 集成、发布或晋升按预期目标执行并读回结果；
- 受影响的公共、架构、合同、安全和恢复文档与同一候选一致。
